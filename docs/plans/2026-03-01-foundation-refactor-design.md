# 工程化改造设计

日期：2026-03-01

## 目标

本轮改造聚焦四件事：
1. 将本地虚拟环境目录约定统一为 `.venv/`
2. 将 Python 包名从 `shejianplus` 重命名为 `shejianplus`
3. 清理 Git 中已跟踪的样例数据与示例视频
4. 建立 `tests/` 骨架和第一批核心逻辑测试

## 背景

当前项目已经具备导入、标注、训练、应用、导出的业务闭环，但工程基础存在明显短板：
- 包名与项目名不一致
- 本地虚拟环境目录与源码视觉混淆
- 样例数据已进入 Git 历史与跟踪区
- 没有自动化测试基础

## 方案对比

### 方案 A：只改 `.venv/`，不改包名

优点：风险小。
缺点：项目名、包名、仓库名继续不一致。

### 方案 B：改 `.venv/` + 改包名 + 同步补测试

优点：一次性把最关键的基础问题处理干净。
缺点：改动面较大，需要隔离分支与系统验证。

### 方案 C：只做测试与数据清理，包名后置

优点：短期最稳。
缺点：包名技术债继续保留，后面还要再做一次全仓重命名。

## 采用方案

采用方案 B。

## 设计要点

1. 保留 `src layout`，仅将目录 `src/shejianplus` 重命名为 `src/shejianplus`。
2. 批量替换源码与入口中的 `shejianplus` 导入路径。
3. `run.py` 继续保持从 `src/` 注入路径，但导入目标改为 `shejianplus.main`。
4. 本地虚拟环境目录约定改为 `.venv/`，文档与 `.gitignore` 同步更新。
5. Git 清理范围包括：
- `workspace/demo_project`
- `56val12times-2.avi`
6. 新建 `tests/`，首批覆盖纯逻辑模块：
- `keypoint_schema`
- `ema_filter`
- `scale_converter`
- `inference_session_exporter` / `exporter`

## 风险控制

1. 在独立 worktree 中实施，避免影响当前工作目录。
2. 先做包名重命名与导入修复，再做测试。
3. 数据清理先在当前跟踪层处理，不做历史重写。
4. 每完成一个阶段都执行语法检查与测试。
