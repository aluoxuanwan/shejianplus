# 射箭Plus 协作文档设计

日期：2026-03-01

## 目标

为 `shejianplus` 项目补充一份中文 `CONTRIBUTING.md`，让两人协作时对分支策略、提交规范、合并流程和最小自测有统一约定，并覆盖本项目的大模型文件、`workspace/` 目录和文档同步等特殊约束。

## 背景

当前仓库已经具备 `main` 分支并开始接入 GitHub 远程仓库，但缺少正式的协作说明。用户已经明确了双人协作方式：

1. `main` 只放可运行版本。
2. `dev` 作为日常集成分支。
3. 每个功能使用独立 `feature/*` 分支。
4. 合并前做最小自测。
5. 模型权重和训练产物不进入 Git。

## 可选方案

### 方案 A：极简规范

只写 Git 基本流程和提交信息规范。

优点：
- 最快落地
- 文档最短

缺点：
- 无法覆盖本项目的大文件、训练产物和文档同步要求
- 后续仍需补充项目特有说明

### 方案 B：平衡规范

写 Git 协作流程，同时加入本项目特有约束和最小检查。

优点：
- 与当前项目状态最贴合
- 既能马上执行，也便于后续加 CI

缺点：
- 比极简版稍长，但仍可控制在一份短文档内

### 方案 C：完整团队手册

加入更完整的评审、发布、Issue、代码风格和测试策略。

优点：
- 最全面

缺点：
- 对当前双人项目偏重
- 会增加维护成本

## 采用方案

采用方案 B：平衡规范。

## 文档结构

`CONTRIBUTING.md` 采用以下结构：

1. 协作目标与分支职责
2. 日常协作流程
3. 提交信息规范
4. Pull Request 规范
5. 本地最小自测
6. 项目特殊约定
7. 推荐分工
8. 常用 Git 命令速查

## 写作原则

1. 仅用中文。
2. 强调可执行性，尽量给出直接可复制的命令。
3. 避免写空泛原则，优先写具体规则和例子。
4. 不引入当前仓库尚未建立的重型流程，例如强制单元测试门禁或复杂发布规范。
